# VNE RAMOK 23 — UNIFIED ORIGINAL 3D & PORTFOLIO BACKEND

**Новая версия:** единый оригинальный 3D-манекен и 6 предметов одежды/аксессуаров в GLB; одинаковые позы и координаты, объёмные рукава и обувь, вращение на 360°. Новые модели занимают менее 160 КБ в сумме и загружаются по необходимости.

**Публичная демоверсия:** сервер может работать с переменной `PUBLIC_DEMO=1`. В этом режиме можно изучить каталог, собрать образ, оформить вымышленную заявку и получить анимированный чек. Личные данные НЕ сохраняются, регистрация и админские операции закрыты. Для полной локальной демонстрации (аккаунты, заказы, админка, SQLite) запустите без `PUBLIC_DEMO`.

**Запуск Windows:** `start_windows.bat` → `http://localhost:3000`. Node.js 22.13+.

**Размещение:** инструкция в [docs/DEPLOY_23.md](docs/DEPLOY_23.md), конфигурация `Dockerfile` и `render.yaml`. Публикация на внешнем сервере не выполнена — нужен GitHub/аккаунт хостинга.

**Тесты:** `npm test` — браузерные/модульные проверки, реальные HTTP-тесты SQLite и отдельная проверка публичного деморежима. Live WebGL-рендер на Windows стоит дополнительно проверить визуально, так как среда тестирования ограничивает доступ Chromium к localhost.

## Быстрый старт

Нужен [Node.js 22.13 или новее](https://nodejs.org/) (используется встроенный
`node:sqlite`, внешние npm-зависимости не нужны).

```bash
npm start
```

Откройте **http://localhost:3000**. Не открывайте `index.html` двойным
кликом, если нужны аккаунты, заявки и админка — они работают только через
сервер; как `file://`-страница сайт по-прежнему рабочий (каталог, LOOKBOOK,
OUTFIT STUDIO, анимации, корзина), но оформление в этом режиме — только
демонстрация, без сервера заявки никуда не отправляются.

На Windows то же самое можно сделать двойным кликом по `start_windows.bat`.

Чтобы создать свой первый админ-аккаунт, остановите сервер (Ctrl+C) и
выполните:

```bash
npm run admin:setup
```

Введите email, имя и пароль (от 12 символов) — он не зашит в код или в
репозиторий, вводится видимо в консоли при настройке. Затем снова `npm
start` и откройте `http://localhost:3000/admin.html`.

## Демо-аккаунты

В репозитории **не хранится** ни одного логина или пароля — локальная
SQLite-база (`data/`) создаётся пустой при первом запуске и исключена из
git (`.gitignore`). Админ-аккаунт создаётся командой выше; аккаунт
покупателя — обычной регистрацией на витрине (кнопка «Профиль»). Оба вида
данных остаются только на вашей машине.

## Технологии

| Слой | Технология |
|---|---|
| Frontend | Vanilla JavaScript (classic `<script>`, без сборщика и фреймворка), CSS custom properties, `IntersectionObserver`, `<dialog>`, WebGL для 3D Outfit Studio |
| Backend | Node.js 22+, встроенный `node:sqlite` (без ORM и без npm-зависимостей) |
| Авторизация | `scrypt`-хэш пароля, сессионная cookie `HttpOnly`/`SameSite=Strict`, rate-limit на вход |
| Тесты | Собственный zero-dependency test runner + интеграционные тесты поверх реального HTTP-сервера |
| QA / скриншоты | Playwright (headless Chromium) — ручные smoke-тесты и `tools/capture-screenshots.js` |
| Изображения | WebP, `loading="lazy"` на карточках каталога, `fetchpriority="high"` на LCP-изображении хиро |

Зависимостей в `package.json` нет вообще — ни одной. Это осознанное
ограничение: весь проект построен на том, что уже есть в браузере и в
Node.js, без abstraction layer конкретного фреймворка.

## Архитектура

**Frontend.** Раньше вся логика магазина жила в одном файле (`app.js`); он
разделён на шесть модулей с одной зоной ответственности каждый:

- `shared.js` — общие утилиты (`$`, `money`, `esc`, рендер визуала товара,
  работа с localStorage, тосты, диалоги). Должен грузиться первым.
- `catalog.js` — фильтры, сортировка, поиск, сетка каталога.
- `product-detail.js` — диалог карточки товара, галерея с кроссфейдом и
  зумом, выбор цвета/размера.
- `cart-panel.js` — корзина-панель, анимация «улетания» товара в корзину.
- `drop-stack.js` — карусель «Новый дроп».
- `bridge.js` — запускает рендер при загрузке страницы и публикует
  `window.VRStore` — явный, задокументированный мост для всего нового кода.

Модули всё ещё загружаются как классические `<script defer>`-теги и
по-прежнему делят часть состояния через обычные переменные верхнего уровня
(так работал JavaScript до модулей) — это намеренно сохранено, потому что
`wardrobe.js` и `storefront.js` читают `cart`, `money`, `toast` и другие
имена напрямую, и это поведение покрыто тестами (`tests/wardrobe.test.js`
эмулирует именно эту среду через небольшой VM-харнесс). `window.VRStore` —
это не замена этому механизму, а явная точка входа для всего, что
добавляется поверх.

**Backend.** `server.js` сократился с 227 строк монолита до тонкой точки
входа (~70 строк): заголовки безопасности, same-origin/CSRF-проверка,
маршрутизация по `Map`, собранной из массивов роутов:

```
server/
├── http-utils.js   — HttpError, парсинг JSON, валидация, таблица MIME
├── auth.js         — сессии, requireLogin/requireAdmin, scrypt-хэш
├── validators.js   — validProduct(), checkedOrder() (цена и остаток — только с сервера)
├── static.js       — отдача статики по строгому allow-list
└── routes/
    ├── catalog.js  — здоровье сервера, список товаров
    ├── account.js  — регистрация, вход, профиль, избранное
    ├── orders.js   — создание и просмотр заказов
    └── admin.js    — товары, заказы, статистика, загрузка фото
```

Такое разбиение по маршрутам, а не по вертикали одного файла — сознательный
выбор: каждый роут проверяется теми же интеграционными тестами, что
запускают настоящий `node server.js` и бьют по нему реальным HTTP, поэтому
рефакторинг был безопасным, а не «на глаз».

**Чего я сознательно не стал трогать.** `admin.js`, `wardrobe.js`,
`motion.js` и `storefront.js` уже были файлами с одной зоной
ответственности, просто в плотном стиле «одно выражение — одна строка».
Переписывать их построчно ради единообразия стиля означало бы лишний риск
без выигрыша в структуре — решение явно зафиксировано здесь, а не спрятано.

- `index.html`, `styles.css`, `motion.css`, `wardrobe.css`, `commerce.css` — витрина и стили.

- `server-catalog.js` — fallback для `file://`; при `npm start` сервер отдаёт по этому URL актуальный ассортимент из БД.

- `tests/` — автоматические проверки.

- `assets/design-reference.png` — исходный визуальный референс/бриф, с которого начинался проект; в самом магазине не используется, оставлен для истории и кейс-стади.

## Тесты

```bash
npm test
```

30 unit-тестов для корзины, демо-оплаты и конструктора образов (включая
VM-харнесс, который воспроизводит совместное использование глобальных
переменных между classic-скриптами без фактической загрузки `shared.js`) +
9 интеграционных тестов, которые поднимают настоящий `node server.js` и
проверяют его по HTTP: регистрация, избранное, создание заказа, проверка
цены/размера на сервере, админский вход, отмена заказа с возвратом
остатка, загрузка фото с проверкой по magic bytes, безопасность путей
статики. Интеграционные тесты создают отдельную временную SQLite-базу и не
трогают ваши реальные локальные данные.

## Безопасный деплой демо-версии

Встроенный сервер по умолчанию слушает только `127.0.0.1` — это осознанно
и **не должно** просто выставляться в интернет как есть (см. раздел ниже).
Если вы всё же разворачиваете демо на доступном извне хосте (например, для
показа клиенту по ссылке):

1. Поставьте перед Node.js обратный прокси с TLS (Caddy / nginx / облачный
   балансировщик) — сам проект HTTPS не терминирует.
2. Не публикуйте `data/` и `uploads/` — они уже в `.gitignore`, но при
   деплое проверьте, что хостинг их тоже не коммитит и не светит напрямую
   как статику.
3. Создавайте админ-аккаунт **на целевом сервере** через `npm run
   admin:setup`, а не копированием локальной базы — не переносите тестовые
   пароли между окружениями.
4. Явно укажите в интерфейсе (он уже это делает), что это демо без
   реальной оплаты — не выдавайте учебный прототип за работающий магазин.
5. Секретов в коде нет и быть не должно: сессионный секрет не хранится в
   репозитории, а каждый запуск сервера использует собственный `data/`.
6. Даже для демо-показа ограничьте доступ (basic auth на прокси или
   IP-allowlist), если каталог/контент не предназначен для публичного
   индекса поисковиков.

## Что сознательно не сделано

1. **Платежи**: выбор и подключение официального провайдера (Stripe /
   iyzico / другой, подходящий для юридической страны продавца),
   серверная обработка вебхуков с проверкой подписи, идемпотентность,
   возвраты. Статус платежа всегда `not_connected`, автоматического
   подтверждения оплаты нет.
2. **Доставка**: тарифы и сроки реальных служб, трек-номера, политика
   доставки/возврата/обмена. Текущие тарифы (390 ₽ стандартная, бесплатно
   от 12 000 ₽, 890 ₽ экспресс) — вымышленные значения прототипа.
3. **Право и данные**: реальные реквизиты продавца, пользовательское
   соглашение, обработка персональных данных, cookie-политика,
   региональные требования (включая GDPR/аналоги, если применимо). Введённые
   в демо данные сохраняются **только в локальной SQLite на машине, где
   запущен сервер** — не вводите в демо реальные личные данные.
4. **Безопасность и эксплуатация**: TLS/HTTPS-терминация, управление
   секретами, резервное копирование, логирование, полноценные
   CSRF-токены, аудит загрузок изображений, мониторинг. Сервер по
   умолчанию слушает только `127.0.0.1` и не предназначен для прямого
   выхода в интернет.
5. **Контент**: остаток по каждой комбинации размер×цвет (сейчас общий
   остаток на товар), проверенные фотографии изделий, точная размерная
   сетка в см, состав, реальные цены, права на контент.
6. **SEO и запуск**: реальный домен и canonical URL, sitemap, robots.txt,
   публичный хостинг и база, QA в реальных браузерах на реальных
   устройствах (здесь — Playwright/Chromium).
